# 端末間同期の設計

連絡通知のスターと一部のアプリ内データを、同じ利用者の複数の端末で共有する仕組みの設計です。More Better Gakujo 側ではサーバーを運用しません。標準の方法は「Google ドライブで同期」ボタンで、本人の Google ドライブにあるアプリ専用の領域を使います。自分のサーバーを使いたい人向けに、WebDAV と S3 互換も詳細設定に残しています。どの方式でも、端末ごとに暗号化したファイルを置き、他の端末のファイルを読み込んでマージします。

## 現在の状態

- `star-sync`（WebDAV/S3）、`star-sync-google`（Google ドライブ）、`google-sync-extras`（同期する項目の追加、同期先のバックアップ、ダウンロードの Google ドライブ保存）のブランチは main に統合済み。v0.70.6 には含まれておらず、次のリリースに含める予定
- 実装は `lib/src/star_sync/` と、設定画面の「スターの端末間同期」（`lib/src/widgets/star_sync_section.dart`）
- 次のタグ付きリリースでは、リリース workflow が Google の OAuth クライアント ID を組み込むため、Google ドライブも選べる予定。クライアントの登録手順は [release.md](release.md) の「Google OAuth クライアント」にある
- 実際のサーバーやアカウントで確かめた範囲は、末尾の「確認できた範囲」にある

## 確定した仕様

- **同期先は WebDAV と S3 互換の両方に対応する。** WebDAV は Nextcloud、NAS、InfiniCLOUD などで、URL とパスワードだけで始められます。S3 互換は Cloudflare R2、Backblaze B2、MinIO などを想定します。
- **端末ごとに1ファイルを書き、共有ファイルを上書きしない。** 条件付き書き込み（`If-Match`）は AWS S3 などでは使えますが、R2 と B2 は公式資料で対応を確認できませんでした。ヘッダーを黙って無視する実装があっても変更が消えないよう、書き込みの競合そのものが起きない構成にします。
- **スターで同期するのは ID と件名だけ。** 本文、送信者、ジャンル、期間、掲載日は端末内にだけ保存します。他の端末で付いたスターは件名だけで表示し、メッセージを開いたときに既存の `refreshStarredMessage` で本文を補います。
- **暗号化を必須にする。** 件名にも人名や手続きの内容が含まれうるため、同期先の管理者から中身を読めない状態にします。鍵は WebDAV/S3 ではパスフレーズから作り、Google ドライブでは自動で作ってペアリングコードで別の端末に渡します。
- **同期は設定したときの学情アカウントに結び付ける。** 同期を使うにはログイン ID の保存が必要です。ログイン ID が変わったり消えたりしたら、通信もスター一覧の書き換えもせずに同期を止めます。元の ID に戻った後も、変更期間中のスターを同期に含めるか、前回の同期状態に戻すかを選ぶまで再開しません。アカウント変更前に確認待ちを保存し、同じアカウントのままで確認待ちの解除に失敗した場合も確認画面を表示します。

## 同期する項目

スターのほかに、次の4つの項目を同期します。設定画面の「同期する項目」で、項目ごとにオン/オフできます。項目ごとの暗号化したファイルは、1つ 8 MiB までです。

| 項目 | 同期するもの | 規則 |
|---|---|---|
| お気に入り | ページの URL、タイトル、追加した日時 | 追加した日時の新しい順に30件まで |
| 設定 | 機能のオン/オフ（連絡通知のスターの設定を除く）、カレンダー連携の設定、連絡通知の除外キーワード、通知の対象と通知の設定 | 設定後の初回の同期では、同期先の値を優先する |
| レポート下書き | WebView に保存したレポートの下書き | |
| 通知済みの締切 | OS 通知を出した提出期限のキーと日時 | 追加だけで、削除は同期しない。新しい順に1000件まで |

項目ごとに、マージ規則は「端末ファイルの中身とマージ規則」と同じ考え方（1件ごとに勝者を決め、削除はマーカーとして残す）を使います。端末内への反映は、読み込んだときから端末内のデータが変わっていない場合だけ行い、変わっていれば次の同期でやり直します。

## 同期先のファイル構成

利用者が指定したフォルダ（WebDAV の URL、または S3 のバケットとプレフィックス）の下に次を置きます。

```
<指定フォルダ>/more-better-gakujo/
  stars/keyring.json          共有の鍵情報（パスフレーズで包んだデータ鍵）
  stars/devices/<deviceId>    端末ごとのスターの暗号化ファイル
  sync/<項目名>/<deviceId>     端末ごとの、同期する項目の暗号化ファイル
  backups/<deviceId>          端末ごとの、同期先のバックアップ
```

`deviceId` はインストールごとにランダムに作り、端末内の安全な保存領域に置きます。バックアップには含めません。含めると、バックアップを復元した別の端末が同じファイルに書き込み、1ファイルに1台だけが書くという前提が崩れるためです。

## 端末ファイルの中身とマージ規則

設定したときの初回の同期では、他の端末に存在するキーはリモートの値を採用し、存在しないローカルのキーと、復元で指定したキーは編集として同期します。

暗号化前の中身は次の形です。

```json
{
  "schema": 1,
  "deviceId": "…",
  "writtenAt": "2026-10-31T12:00:00Z",
  "clock": 42,
  "stars": {
    "1|23|456": {
      "title": "…",
      "starred": true,
      "starredAt": "2026-10-30T09:00:00Z",
      "clock": 41,
      "deviceId": "…"
    }
  }
}
```

- **1件ごとに勝者を決める。** 同じ ID のレコードは `clock`（ランポート時計）が大きい方を採用し、同じ値なら `deviceId` の辞書順で決めます。端末の時計がずれていても結果が変わらないよう、壁時計の時刻は判定に使いません。
- **削除は削除マーカーとして残す。** マーカーは (clock, deviceId, id) の新しい順に最大1000件を保持し、件名を空にします。古いマーカーが上限で消えた後は、オフラインだった端末からスターが復活する場合があります。
- **上限300件は全端末で同じ規則で切る。** マージ後は starredAt の新しい順、同時刻なら ID の昇順に300件残し、超過分はこの端末の新しい削除マーカーに変えます。
- **端末内の本文を消さない。** マージで変わるのはスターの状態と件名だけです。勝者の件名が空なら端末内の件名を残します。
- **各端末は自分のマージ結果を書く。** 他の端末の内容を取り込んだ状態で自分のファイルを書くので、使われなくなった端末のファイルが残っても害はありません。設定画面から古い端末のファイルを削除できます。

`GakujoActivityStore` にある既存の操作と、同期での扱いは次のとおりです。

| 既存の操作 | 同期上の扱い |
|---|---|
| `toggleStarredMessage` / `upsertStarredMessage` / `removeStarredMessage` | 利用者の編集として `clock` を進める |
| `refreshStarredMessage`（詳細表示で中身を補う） | 端末内の補完なので `clock` を進めない |
| `replaceStarredMessages`（バックアップ復元） | 復元したスターは新しい編集として追加・更新し、バックアップにないスターは削除扱いにしない |
| `replaceStarredMessages(const [])`（データをすべて削除） | 先に同期を無効にし、空の一覧を他の端末への削除として伝えない |

実装では各操作に同期処理を差し込まず、同期のたびに端末内のスター一覧と前回のマージ結果を比べて、この端末での追加・削除を導きます（`reconcileLocalStars`）。上限300件で端末内から押し出されたスターは、削除として扱いません。

## 同期の流れ

1. `devices/` を一覧する。
2. 前回から変わったファイルだけを取得する（ETag や更新日時を端末内に記録して比較）。
3. ヘッダーの鍵 ID が現在の鍵と異なるファイルは、リセットした端末の旧鍵の掃除を除き、復号も削除もせず、警告の件数に含めずにスキップする。それ以外は復号して認証タグを検証し、形式不正・認証失敗・アカウント不一致のファイルは残してスキップし、その件数を警告として表示する。旧鍵の掃除以外でファイルを削除するのは、利用者が「同期データをリセット」（全端末のファイルと鍵ファイルを消す）を選んだときか、端末一覧から明示的に削除したときだけ。
4. 端末内のスターとマージし、端末内の保存領域へ書き戻してから同期状態を保存する。同期状態の保存に失敗した場合も、ID とスターを付けた日時が既知の記録と一致すれば新しい編集として扱わない。ただし、バックアップ復元で削除マーカーと一致したスターは、新しい編集として復活させる。
5. 自分のファイルの内容が変わった場合だけ書き込む。

同期のきっかけは、起動時、アプリに戻ったとき、スターを付け外ししてから約5秒後、設定画面の手動同期、容量不足や Drive の利用制限後の再試行です。通信に失敗しても端末内のスターが正本なので、操作はそのまま続けられます。設定画面には最終同期時刻と直近のエラーを表示します。

- 設定と状態の保存に失敗した場合は両方の削除を試み、端末内のスターは消さない
- 設定を保存した後の初回の同期に失敗しても、設定は有効なまま残り、エラーを表示する
- 端末内のスターの消去を選んだときは、その時点の ID とスターを付けた日時を保留状態として保存し、両方が一致するスターだけを消す。選んだ後に追加・再追加したスターは残る。保存や消去に失敗した場合は、次の同期か設定の読み込みのときに再試行する

## 暗号化

- **データ鍵**：256ビットのランダムな鍵で、端末ファイルを AES-256-GCM で暗号化します。追加認証データにはファイルのヘッダーと `deviceId` を入れ、ファイル名の付け替えを検出します。
- **keyring.json**：パスフレーズから Argon2id で作った鍵でデータ鍵を包んで保存します。KDF のパラメータ、ソルト、鍵 ID（`keyId`）は平文で持ちます。
- **新しい端末の参加**：接続設定とパスフレーズを入力し、`keyring.json` からデータ鍵を取り出します。取り出したデータ鍵は端末内の安全な保存領域に置き、パスフレーズ自体は保存しません。
- **最初の端末**：`keyring.json` がなければ作成します。2台が同時に作成した場合に備え、作成後に読み直し、別の鍵があればそちらを採用してから端末ファイルを書きます。
- **パスフレーズの変更**：データ鍵を包み直して `keyring.json` だけを書き換えます。端末ファイルは作り直しません。
- **パスフレーズを忘れた場合**：同期データは復元できません。同期をリセットして、同期先の `stars/` を作り直します。端末内のスターは残るため、リセット後に再び共有できます。設定画面にもこの点を書いています。

## 接続方式ごとの実装

どちらの方式も Dart 標準の `dart:io` の `HttpClient` を使い、HTTP 用の依存パッケージは追加しません。接続情報は `FlutterSecureStorage` に保存し、バックアップには含めません。HTTPS 以外の接続は受け付けません。同期先は、学情や大学関連のホスト向けの `AllowedWebOrigins` には含まれないので、同期用のクライアントは許可リストを広げず、設定で入力されたホストにだけ接続します。

- **WebDAV**：URL、ユーザー名、パスワード（アプリパスワードを推奨）。`PROPFIND`（Depth: 1）で一覧し、`GET`、`PUT`、`MKCOL` を使います。
- **S3 互換**：エンドポイント、リージョン（R2 は `auto`）、バケット、プレフィックス、アクセスキー、シークレット、パス形式の URL の切り替え（MinIO・R2 向け）。署名の SigV4 は既存の `crypto` パッケージの HMAC-SHA256 で実装し、`ListObjectsV2`、`GetObject`、`PutObject` を使います。案内では、そのバケットとプレフィックスに限定したキーを作るよう勧めます。

## Google ドライブ同期

利用者が用意するのは Google アカウントだけです。保存先は Drive API の `appDataFolder`（このアプリだけが読み書きできる非表示の領域）で、スコープは `drive.appdata` と、接続中のアカウントを表示するための `openid`・`email` です。`drive.appdata` は Google の分類で非機密のスコープなので、必要なのは基本的な OAuth 審査だけです。

- **ログイン**：Windows/macOS は既定のブラウザを開き、端末内（`127.0.0.1`）で結果を受け取る方式（PKCE と state 付き）です。更新用トークンだけを `FlutterSecureStorage` に保存します。端末内で結果を待つ間は、パスが `/` で state が一致する要求だけを扱い、それ以外の要求は無視します。Android/iOS は `google_sign_in` を使います。
- **ログアウト**：Windows/macOS は、再起動後も保存済みの更新用トークンの取り消しを試み、端末内のトークンを削除します。iOS は必要に応じて UI を出さずにアカウントを復元して取り消します。Android のプラグインは復元時に UI を表示する可能性があるため、再起動後などアカウントがメモリにない場合は、取り消せなかったことを通知します。取り消しに失敗した場合は、Google アカウントの接続設定でも確認してください。
- **ファイル**：Drive のファイル名に、相対パス（`stars/keyring.json`、`stars/devices/<端末ID>` など）をそのまま使います。2台が同時に作って同名のファイルが重複した場合は、作成日時が最も古いものを正とします。
- **鍵の受け渡し（ペアリングコード）**：パスフレーズは使いません。1台目が鍵を自動で作り、`keyring.json` には鍵 ID だけを置きます。2台目は、1台目の「別の端末を追加」に表示される QR コード（`mbgstar:` + コード）を読み取るか、コードを入力して鍵を受け取ります。コードは鍵 ID・鍵・チェックサムを Base32 にしたもので、知っている人は同期データを読めます。
- **リセット**：同期先の全端末のファイルと鍵ファイルを消し、新しい鍵とコードを作ります。他の端末は新しいコードの入力が必要になります。
- **ボタンを表示する条件**：OAuth クライアント ID を組み込んだビルドでだけ「Google ドライブで同期」を表示します。組み込んでいないビルドでは WebDAV/S3 だけが選べます。

### Drive API の上限への対策

自動保存は、1つのファイルの推定費用だけでソフト上限を超える場合、すぐに見送ります（最大 2,352 MiB、約 2.3 GiB / 2.47 GB）。自動処理の各リクエストも、ソフト上限を超えないかを検査します。

Drive API の利用量は、端末ごとに「直近24時間」（1時間単位の区切り）で記録します。

- 自動処理は、推定した開始費用を加えると直近24時間で 15,000 ユニットを超える場合に止まる。古い利用分が24時間の枠から外れた時点（＋最大30分のランダムな遅れ）で、同期を再開する
- 手動の操作を含め、直近24時間で 25,000 ユニットを超えるリクエストは送らない
- Google Drive の各リクエストは送る前に計上し、再試行も数える。files.list は 100、files.get のメタデータは 5、alt=media は 200、create/update/delete は 50、再開可能アップロードのセッション開始・各チャンク・状態確認はそれぞれ 50
- WebDAV/S3 は対象外
- アプリのデータの消去や再インストール、端末の時計の変更で記録が消えたりずれたりした場合は、この上限の保証の対象外

直近24時間で数えるので、Google の集計日を含むどの24時間を取っても、1台の利用量はハード上限の 25,000 ユニット以下に収まります。ローカルの日付で区切ると、日付の変わり目をまたいで1集計日に最大2日分を使えてしまうため、この方式にしました。400,000,000 ユニットの1日の無料枠には、毎日ハード上限まで使う端末なら約 16,000 台、ソフト上限までなら約 26,000 台が収まります。同じプロジェクトを使う他のアプリや端末があれば、それも合算します。

この端末内の上限は、正しく動いているアプリに対する歯止めです。端末の時計を24時間以上進めると直近の利用分が数えられなくなるなど、端末側の操作で回避できる余地は残ります。そもそも OAuth クライアント ID は配布アプリに含まれ、誰でも取り出せるため、意図的な使い込みは端末側では防げません。プロジェクト全体の最後の守りは、Google Cloud 側の設定（課金アカウントを紐づけない、割り当ての上限を無料枠より低くする）です。2026年の課金の詳細が Google から公表されたら、これらの設定と、超過したときの挙動を確認する必要があります。

1回あたりと頻度の抑え方は次のとおりです。

- **起動時と復帰時を分散する**：起動時と復帰時の同期は 0〜90 秒に分散し、ローカルの変更があれば待機を打ち切ります。
- **1回の同期を軽くする**：一覧の取得は通常1回の同期につき1回だけにし、鍵ファイルと端末ファイルの有無と更新はその一覧で判断します。鍵ファイルは更新番号が変わったときだけ、他の端末のファイルも変わったものだけを取得します。自分のファイルは内容が変わったときだけアップロードします。
- **頻度を抑える**：起動時と復帰時の同期は、前回の同期から2分以内なら省き、1台につき1日120回までとします。ローカルの変更は5秒待ってまとめて送ります。
- **断られたら控える**：混雑やサーバーエラーで断られたら1分間は同期を控え、続けて断られるたびに2倍（最大60分）にします。その間の変更は記録し、控える時間が明けたら送ります。

参考：[Drive API の使用量上限](https://developers.google.com/workspace/drive/api/guides/limits)

## ログイン ID と同期の結び付け

同期とダウンロードの Google ドライブ保存は、学情のログインフォームで送信された ID のハッシュを、現在のセッションに結び付けて使います。ID の原文やパスワードは、この識別情報として保存しません。

- 送信された ID は、そのあとの許可された学情のページで「ログアウト」が表示されているのを確かめてから、セッションに結び付ける。入力欄がないだけのページや、2段階認証の画面では確認待ちのまま
- ログインフォームは login.do へ送信されるので、その遷移では送信された ID を保持する
- 次の場合は、送信された ID を破棄する
  - 送信後のページに再びログインフォームが表示された（ログインの失敗）
  - 送信後30秒以内にページの読み込みが始まらない。ページ側で取り消された送信は数えない
  - 読み込みが通信エラーで失敗した
  - 送信から5分たっても確認できない
- ログインやタイムアウトの画面への遷移が始まったとき、認証の入力欄を見つけたとき、異なる ID が送信されたときは、識別情報をすぐに無効にし、同期と Drive 保存を止める
- 再起動後は、保存済みの識別情報を、認証済みのページで確かめるまで使わない。最初のページがログイン画面なら破棄する
- ダウンロードは、開始したときの識別情報に結び付ける
- 同期による端末内への保存と、同期先のバックアップからの復元では、書き込みのたびに直前でアカウントを確かめる。途中で変わった場合は復元を巻き戻す
- 同期の初期設定には、保存済みのログイン ID と現在のセッションが一致していることが必要

## 同期先のバックアップ

同期先には、端末ごとに1つのバックアップを、同期のデータ鍵で暗号化して保存します。設定画面から作成・一覧表示・復元ができます。

- 含めるのは、スター（ID、件名、スターを付けた日時）と、同期の対象として有効にしているお気に入り、設定、通知済みの締切のキーだけ
- ダウンロード履歴、失敗したダウンロード、期限、変更履歴、レポート一覧のキャッシュ、課題、レポート下書きは含めず、復元のときにも無視する
- 復元できる上限の 5 MiB を超えるアップロードは拒否し、前のバックアップを置き換えない
- ローカルの自動バックアップに成功したあと、前回の同期先への保存から24時間以上たっていれば、バックグラウンドでも保存する。同期先への自動のアップロードは24時間に1回まで
- ローカルのファイルのバックアップの内容は、これまでどおり

復元では、既存のバックアップ復元と同じ確認と処理を使います。

- 復元は、確認したときのアカウントに結び付ける
- 同期対象の項目はバックアップの値で上書き・追加し、バックアップにないキーは削除しない。バックアップの後に他の端末で追加された項目も残る
- 復元した項目は、ローカルの変更として同期する
- 同期先からスターを復元するときは、同じ ID の端末内の本文などを残す

Google ドライブを使う場合は、全端末を失ったときの復旧に必要な「別の端末を追加」のコードを安全に保管してください。

## ダウンロードの Google ドライブ保存

任意の設定を有効にすると、Google の `drive.file` 権限を追加で求め、ダウンロードしたファイルを `More Better Gakujo/科目名/` に保存します。端末内への保存を優先し、読み取りやアップロードに失敗した場合は画面に通知します。

iOS と macOS では、保存先フォルダのセキュリティスコープ外からファイルを読み取れないため、ダウンロードしたバイト列をアップロード終了までメモリに保持して使います。

### 使うフォルダ

- 本人が所有し、共有していないフォルダだけを使う。該当するフォルダがなければ新しく作る
- キャッシュ済みのフォルダも、保存のたびに所有・共有・ゴミ箱の状態を確かめ、使えなくなっていれば探し直す
- アップロード後も両方のフォルダを確かめ、使えなくなっていれば保存したファイルの削除を試みる
- 同名のファイルがあり、共有されておらず MD5 が一致する場合は、重複して保存しない

### アカウントへの結び付け

- 保存は、保存したログイン ID のハッシュと、Google のメールアドレスの両方に結び付ける
- 保存の対象になるのは、ダウンロードを始めたときのアカウントの識別情報がこの結び付けと一致し、アップロード中も変わらないものだけ
- 別の Google アカウントに変えると、この設定はオフになる。Google 同期も、設定したときの Google アカウントでなければ使えない
- 設定をオフにするかログアウトすると、待機中のアップロードを破棄し、実行中の転送を中止する
- 古い形式の設定値は、アカウントに結び付けないまま安全な保存領域に移す。そのため、明示的に有効にし直す必要がある

### 失われた応答の回復と確認待ち

- 再開可能なアップロードのセッションを始める前に、アカウント、フォルダの ID、ファイル名、サイズ、MD5、開始時刻、ランダムなアプリのプロパティを安全な保存領域に記録する
- 最後の応答が失われた場合は、そのプロパティとメタデータが一致するファイルを探して回復する。関係のないファイルは、一致しても削除しない
- 最終チャンクの送信を試みる前に失敗した場合は、確認待ちを直ちに削除する
- ファイルが見つからない確認待ちは新しい保存を妨げず、開始から24時間を過ぎたら削除する。確認や削除に失敗した場合は確認待ちとして残し、新しい保存を止める。最後の応答が失われてから24時間を過ぎて Drive の一覧に現れたファイルは、以後確認されない。
- 見つかったアップロードは、フォルダが非公開だと確かめられるか、ファイルが削除されるまで、Google アカウントごとにファイルとフォルダの ID を安全な保存領域に残す。起動時とそのあとのアップロードのときに、自動処理の利用量の範囲内で再試行する。確認を先送りしたときは利用者に通知する
- 起動時とアップロードの前には、Drive 保存がオフでも、学情との結び付けが変わっていても、ログイン中の Google アカウントの確認待ちを処理する
- 残った確認待ちは起動時に知らせる。保存をオフにするときとログアウトするときは、先に確認するかを尋ねる
- Android で Drive にアップロードするときは、content URI を最大 8 MiB ずつ読み込む

## 実装時に決めたこと

- **同期しない間のアカウント変更**：別のログイン ID に変えて元に戻した場合も、次の同期の前に、ローカルのスターを残すか破棄するかを選びます。メッセージ ID がアカウントをまたいで一意かは未検証のため、破棄して戻すときは端末内の本文などを再利用せず、同期のレコードだけから組み立て直します。本文はメッセージを開いたときに補います。
- **リセット後の旧鍵のファイル**：リセットした端末だけが、削除の前に確認した鍵 ID を7日間記録し、遅れて書き込まれた他の端末の同じ鍵 ID のファイルを削除します。ヘッダーは未認証なので、記録した ID と完全に一致するものに限り、削除の直前に取得し直して確かめます。取得し直してから削除するまでの間には、競合の余地が残ります。自分のファイルと、別の鍵 ID のファイルは対象外です。鍵ファイルを読み取れない場合もリセットはできますが、旧鍵の ID は記録できません。
- **暗号ライブラリ**：純粋な Dart 製の `cryptography` を使います（XML の解析には `xml`）。Argon2id（19 MiB・2回）は、開発機の `flutter test` で鍵の作成が約0.14秒、取り出しが約0.09秒でした。UI を止めないよう別の isolate で実行します。モバイルの実機での時間は計っていません。
- **アカウントの取り違えの防止**：ローカルのスターの扱いを選ぶ前の、保存済みのログイン ID から作ったハッシュを、設定が終わるまで照合し、同期の状態と、暗号化した端末ファイルに記録します。同期のたびに、まず今のログイン ID と照合します。違う場合やログイン ID がない場合は、一覧の取得・マージ・端末内への反映・アップロードを一切行わず、設定画面に停止中と表示します。元の ID に戻った場合も、変更期間中のローカルの付け外しを同期に含めるか、前回のマージの状態へ戻すかを利用者が選ぶまで同期しません。他の端末のファイルも、記録されたハッシュが一致しないもの（記録がないものを含む）は取り込みません。
- **設定前の端末内のスター**：スターがある場合、同期に含めるか、空にして始めるかを選べます。
- **空にして始めたときの下書き**：設定のときに「空にして始める」を選び、その時点で下書きを読み取れなかった場合は、次に読み取れるようになった時点で、下書きを読んだりアップロードしたりする前に、保存されている v1・v2 の下書きをすべて消します。保存日時（savedAt）は問いません。
- **設定のときの消去の対象**：登録されたすべての項目のスナップショットを取ります。いま無効にしている項目も含みます。
- **先送りした下書きの消去**：同期の状態とは別に保存するので、同期を無効にしても、アプリのデータを消しても残ります。次に読み取れる学情のページで、選んだ基準時刻までに保存された下書きを消します。
- **Google のメールアドレスのない既存の設定**：Google のメールアドレスを保存していない Google 同期の設定は、同期を一度無効にして設定し直す必要があります。
- **コードやパスフレーズを忘れた場合**：確認したうえで同期先のデータをリセットし、設定をやり直せます。他の端末も接続し直す必要があります。
- **アカウントを間違えたとき**：新しくログインするときはブラウザでアカウント選択を必ず出す。同期を設定済みの再ログインは、設定したアカウントを最初から指定する。同期のアカウントを変えるには、同期を無効にしてから設定し直す。同期を使わずダウンロードの Google ドライブ保存だけを使っている場合は、スイッチをオフにするとログアウトするので、次にオンにするときに選び直せる
- **Google の再ログイン**：ログインが切れた場合は、設定画面から再ログインして同期できます。
- **データをすべて削除**：同期の設定を読み込んで無効にし、接続方式にかかわらず Google からもログアウトします。
- **別の端末を追加**：コードを表示するのは Google ドライブのときだけです。WebDAV/S3 は、接続設定とパスフレーズで参加します。
- **同期を無効にしている間の削除**：その間に外したスターは、同期を再び有効にすると他の端末から戻ることがあります。
- **ペアリングコードのコピー**：コピーしてから60秒後、アプリの一時停止や終了のとき、または「データをすべて削除」を実行したときに、クリップボードの内容がそのコードのままなら消します。
- **同期した設定の端末内での保存**：同期で受け取った設定は、ローカルで変更した設定と同じように適用し、既存の平文のローカルのミラー（`local_prefs.json`）にも保存します。適用するのは同じアカウントのデータだけです。
- **レポート下書きの取り込み**：取り込みは WebView の中で非同期に行います。下書きは、同じ端末のすべてのアカウントで共有する、WebView のオリジン単位のローカルストレージに保存されるので、アカウントを変えたときの確認の対象にしています。

### 既知の制約

- **端末内のデータはアカウントごとに分かれない**：スター・お気に入り・下書きなどの端末内のデータは、同期を入れる前から、学情アカウントごとではなく端末ごとに保存されています。同期を設定した端末を別の人が使うと、同期で受け取った内容もその人から見えます。アカウントの切り替えを検知すると同期は止まり、設定画面で端末内のデータを消せますが、表示そのものは制限しません。設定画面に「共用の端末では同期を設定しないでください」と表示します。「データをすべて削除」と保存データのリセットは、これまでどおり、WebView に保存されたレポート下書きと自動バックアップのファイルを削除しません。そのため、同期で受け取った下書き、お気に入り・設定、通知済みの締切のキーも、それらに残ります。
- **ログインに失敗した後に戻る操作**：送信した ID は、ログインフォームが再び表示されたときに破棄します。ログインフォームのない画面（アカウントのロックの表示など）でログインが失敗し、その後に履歴を戻って、別の人のセッションがまだ有効なページを開くと、送信した ID がそのセッションに結び付く可能性があります。学情の実際のログインの経路を確かめられないため、ログイン後の画面遷移の連続性までは判定していません。
